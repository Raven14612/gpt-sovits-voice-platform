## 见习内容

本周我继续负责轻量级音色克隆项目的 RTX 50 系主线、真实模型流程和阶段验收。第一周已经完成项目范围、目录结构和外部引擎边界的整理，第二周的重点是把原先只能在 GPT-SoVITS 整合包 WebUI 中完成的操作逐步接入项目，使音频导入、切分、识别、校对、特征提取、训练、权重归档和语音合成形成一条能够实际运行的链路。为了减少重复工作，本周暂停 40 系兼容任务，把设备、时间和测试资源集中到 RTX 5060 Laptop 主机。

周一，我先整理了已有 Citlali 音色的训练证据和正式档案。根据整合包生成的 GPT `.ckpt`、SoVITS `.pth`、参考音频和对应文本，建立了项目可以读取的 `VoiceProfile`。随后通过整合包 API 和项目适配器执行真实合成，检查输出 WAV 的文件大小、采样率、声道和帧数，并进行人工试听。通过这一步，我进一步确认了训练权重、参考音频和提示文本必须成组保存，不能只登记两个权重文件。对于测试替身和已有文件复用，也明确要求不能作为新训练成功的证据。

周二，我使用一份超过一分钟的新音频验证完整的数据处理流程。项目首先把长音频导入部署根目录下的数据集目录，再按照固定参数切分为 17 个适合训练的短句。所有切片经过 FunASR 中文识别后写入标注文件，我逐条检查并修正文字，同时保存人工情绪标签。随后项目依次执行文本与 BERT 特征、HuBERT 与 32 kHz 音频、说话人特征和语义特征提取。为了确认数据没有错位，我检查了切片数量、标注行数、特征文件名和语义记录是否一一对应。处理结果证明，程序已经能够正确理解“长音频是训练输入、短切片是中间产物”，不会把单个五秒片段误当成完整数据集。

周三，我协助补齐音频处理 service 和页面按钮接线。原始音频、处理任务、切片、校对版本、特征和训练准备文件全部改为基于项目部署根目录的相对路径保存，本机整合包位置只存在于不提交仓库的 `engine.local.json` 中。页面可以显示真实任务阶段、日志和失败原因，GPU 忙碌时禁止重复提交。与此同时，我检查了文件管理清单，明确数据集、训练配置、权重、日志和合成结果各自的保存位置，避免后续出现整合包目录、项目目录和临时目录相互混用。

周四，我完成了 GPT-SoVITS 训练命令的项目接入。项目根据已校对数据和特征清单生成独立的 v2Pro 配置，实际执行 GPT 十五轮和 SoVITS 八轮训练。训练期间使用全局 GPU 串行锁，每一阶段记录命令参数、标准输出、错误输出、退出码和超时。训练完成后，程序通过内容摘要检查本次是否真正产生新 checkpoint，并处理 SoVITS 文件名中动态 step 的情况。本次新生成的 GPT 权重约 155 MB，包含 295 个权重项；SoVITS 权重约 135 MB，包含 678 个权重项，两者都可以由整合包运行时加载。

周五，我完成权重归档和项目内合成回归。新音色以 `buer-w2-project` 为独立 ID 归档到 `data/voices`，音色索引中的权重和参考音频均使用项目相对路径。归档后，我通过项目合成页面生成新的 32 kHz 单声道 WAV，并试听确认音色和语句完全正常。完整测试在配置真实音频、真实特征和真实权重后达到 70 项全部通过，无跳过；应用构建、编译检查和 7860 端口启动也通过。至此，第二周实现了从长音频到可用音色再到语音输出的真实技术闭环。

## 见习心得

本周最大的收获是理解了“流程跑通”和“产品接入”之间的差别。整合包可以帮助开发者训练和推理，但普通用户不应该自己填写大量路径、命令和环境变量。项目需要把这些复杂信息转化为数据集、任务、音色和结果等清楚的业务对象，同时仍保留足够日志，让失败可以复现。只有页面、service、适配器、外部引擎和文件索引共同工作，才算真正完成了一个功能。

真实训练也让我更加重视成功判定。进程退出码为零并不足以证明训练成功，目录中存在权重也可能只是旧文件。本周通过训练前后内容摘要、新文件路径、权重加载和归档后合成多重检查，减少了误报成功的可能。checkpoint 临时文件的路径问题同样说明，文件保存位置不是小细节；跨磁盘移动、中文路径和中断清理都会影响长时间训练的可靠性。

我还体会到，项目管理需要根据实际条件及时调整。暂停当前没有必要的 40 系工作后，团队可以集中完成 50 系主线，并用更扎实的证据结束第二周。接下来进入第三周，我会把重点放在合成任务持久化、结果下载与删除、参数复用、连续稳定性和重启恢复上，使已经打通的模型能力成为一套更完整、更容易演示的产品流程。
