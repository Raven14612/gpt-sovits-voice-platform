## 见习内容

本周我主要负责轻量级音色克隆项目的数据服务、任务编排、训练归档和错误处理。第一周完成了数据模型与适配器骨架，本周则需要把这些结构变成可以支持真实流程的后端实现。开发过程中仍然坚持项目环境与 GPT-SoVITS 模型环境分离，所有模型命令都由配置和适配器提供，services 只管理业务状态、路径、日志和输出校验。

周一，我完善了数据集索引服务。数据集的原始音频、切片目录、校对标注、情绪文件和特征清单都通过 `DatasetRecord` 管理，索引写入采用同目录临时文件和原子替换，避免应用中断时破坏已有 JSON。对于不存在的索引、损坏的 JSON、重复记录和并发写入，服务返回稳定结果或明确错误。路径在程序运行时解析为绝对路径，在索引中则尽量保存相对于项目部署根目录的位置，从而支持项目整体移动。

周二，我实现了音频处理和特征提取任务编排。长音频导入后，任务按验证、切分、ASR、文本特征、HuBERT、说话人特征和语义特征依次执行。每个外部命令使用参数数组启动，并记录工作目录、超时时间、标准输出、错误输出和退出码。仅有进程成功还不够，服务还会检查切片、标注和特征是否存在、是否为空以及是否与全部切片一一对应。若中途失败，数据集不会被错误发布为已完成，第二个 GPU 任务也会收到 `GPU_BUSY`。

周三，我完成了训练任务和权重归档的工程实现。训练服务依次运行 GPT 与 SoVITS 阶段，任务状态保存在 JSON 索引中，应用重启时能够识别未结束任务并标记为失败。权重归档前会检查路径范围、扩展名、文件大小、修改时间和内容特征，拒绝空文件、文本占位和外部路径。为了防止把旧权重当作新训练结果，服务在训练前保存内容摘要，训练后要求目标文件内容发生变化。音色档案最后写入，任何训练或复制失败都不会留下 `verified` 音色。

周四，我根据真实 v2Pro 训练配置继续完成动态 checkpoint 接入。GPT 最终权重名称可以提前确定，SoVITS 文件名则包含实际 step，因此服务增加了受控文件名匹配，只允许在本次隔离训练目录中查找匹配权重，并从内容发生变化的文件中选择最终结果。训练页面先调用准备服务生成配置，再把明确的命令、输出规则、超时和参考音频交给训练服务。这样页面不需要了解整合包脚本细节，后端也不依赖人工复制权重。

周五，我配合完成项目级 TTS 和历史服务。合成前会检查正式音色、GPT/SoVITS 权重、情绪参考、参考文本和目标文本，申请全局 GPU 锁后调用整合包 API。只有返回内容通过 WAV 结构检查，才写入成功历史；失败时清理不完整输出。历史索引同样使用原子替换，输出路径限制在项目 `data/outputs` 内。最终，项目真实训练任务进入 `packaging/succeeded`，两份权重被归档并能够再次合成。使用真实素材和真实权重运行回归测试时，70 项测试全部通过。

## 见习心得

本周让我更清楚地认识到，长时间模型任务的后端设计核心是保持状态与文件一致。训练可能在任何阶段失败，如果先写音色档案再复制权重，或者只根据目录存在判断成功，就会留下用户无法使用的记录。因此，操作顺序、原子写入、输出校验和失败清理比简单调用一个训练脚本更重要。

动态 checkpoint 文件名也是一个有代表性的问题。工程代码不能依赖手工计算 step，也不能使用过宽的通配符扫描整个磁盘。本周采用本次运行目录、受控文件名和训练前后内容摘要共同限制查找范围，使自动归档既能适应模型脚本的输出规则，也能避免误用旧文件。这种处理方式可以迁移到其他外部工具接入中。

我也进一步理解了测试替身和真实验证的关系。替身适合稳定覆盖超时、非零退出、缺失文件和 GPU 冲突，但不能证明模型在真实显卡上能够训练。只有将这些工程测试与 CXY 的真实 GPU 训练、权重加载和人工试听结合，结论才完整。第三周我将继续完善推理进程生命周期、合成任务日志、历史删除与复用，以及中断后的恢复检查。
