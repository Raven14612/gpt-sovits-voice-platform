## 见习内容

本周是轻量级音色克隆项目的第一周，我在小组中主要承担后端工程结构、数据模型、任务状态和 GPT-SoVITS 引擎集成方案的整理工作。这个项目不是重新训练一个全新的语音大模型，而是使用外部 GPT-SoVITS 能力，在其上开发一套更适合普通用户的本地操作系统。后端需要把音频处理、数据集、音色训练、语音合成和结果历史这些内容整理成稳定的业务接口，使前端不需要知道具体模型命令，也不需要针对 40 系或 50 系显卡分别编写两套页面。

周一，我先根据项目需求搭建单体 Gradio 工程的基本目录，保留唯一的 `app.py` 启动入口，并划分 `ui`、`services`、`models`、`data`、`assets` 和 `tests` 等模块。小组明确本项目不使用 Vue、React、FastAPI、数据库、Redis 或任务平台，数据主要通过本地文件夹和 JSON 索引保存。这样做可以降低部署难度，也符合四周学生项目的实际工作量。工程骨架建立时，我特别注意不加入假音频、假模型和固定成功返回；尚未实现的功能应明确显示“未接入”，避免页面看似完整但后台没有真实能力。

周二，我参与梳理后端需要管理的主要数据。一个数据集不仅包含原始音频，还包含切分目录、ASR `.list`、人工校对文本和情绪标签；一个音色档案需要记录展示名、内部特征名、来源数据集、GPT 权重、SoVITS 权重、引擎配置和参考音频；一次合成记录需要保存音色、文本、情绪、语速、停顿、输出路径和创建时间。基于这些关系，项目初步建立 `DatasetRecord`、`VoiceProfile`、`EmotionReference`、`GenerationRecord` 和 `TaskRecord` 等数据结构。情绪字段当前只允许 `neutral`、`happy`、`sad`，并要求同一种情绪只保留一条主参考，防止前端和后端对同一标签产生不同理解。

周三，我重点整理模型任务的状态与错误处理。语音项目中的切分、ASR、特征提取、SoVITS 训练、GPT 训练和 TTS 合成所需时间不同，不能简单返回一个“成功”字符串。任务状态统一为等待、执行、成功、失败和取消，训练阶段再细分为检查数据、切分、ASR、文本特征、HuBERT 特征、语义特征、SoVITS 训练、GPT 训练和音色打包。由于没有可靠的总工作量，页面只能显示真实阶段和日志，不能虚构百分比。我还整理了统一错误对象 `AppError`，为配置缺失、GPU 不可用、GPU 忙碌、无效音频、ASR 失败、训练失败、参考音频缺失和合成失败等情况准备清楚的错误码与普通用户能够理解的提示。

周四，我参与制定外部引擎适配方案。项目不能直接复制 CXY 使用的 50 系整合包，也不能在源码中写死个人磁盘路径，因此使用 `engine.local.json` 保存本机的 GPT-SoVITS 根目录和 Python 路径，仓库只提交不含真实路径的配置样例。适配器第一步实现环境探测，检查配置是否存在、模型解释器能否启动、PyTorch 和 CUDA 是否可用、GPU 名称是什么。后续切分、ASR、训练和推理也都由适配器统一调用。这样 CXY 的 50 系环境和 LJQ 的 40 系环境只需要使用不同配置文件，UI 与 services 不需要改动。子进程启动时使用参数列表而不是拼接长字符串，并捕获标准输出、错误输出和退出码，便于后续定位失败原因。

周五，我整理了 GPU 串行和本地文件安全要求。项目默认一次只允许一个 GPU 任务，第二个任务提交时返回 `GPU_BUSY`，避免训练和推理同时占用显存。音频、权重和生成结果不提交 Git，本机配置也加入忽略列表。数据索引使用 JSON，后续写入时需要采用临时文件加替换的原子方式，防止程序中断造成索引损坏。历史页面只能显示真实成功记录，训练或合成失败不能留下成功条目。本周已经完成后端目录、数据模型、配置样例、环境探测骨架、任务锁和无 GPU 基础测试，但切分、ASR、训练和 TTS 的真实命令还需要等待 CXY 提供经过验证的输入输出后继续接入。

## 见习心得

通过本周工作，我认识到后端开发不只是把页面按钮连接到一个 Python 函数。语音模型任务运行时间长、依赖多、输出文件多，而且容易受 GPU、路径、编码和模型版本影响。如果没有统一的数据结构和任务状态，前端很难准确显示过程，出现问题时也无法判断是用户输入错误、环境问题还是模型执行失败。因此，在模型接入之前先建立清楚的边界，能够明显减少后期联调时的重复修改。

我对“环境解耦”也有了更直观的理解。小组四人的显卡并不相同，如果业务代码直接依赖某个整合包目录，那么换一台电脑就可能全部失效。通过配置文件和适配器隔离外部环境后，后端只需要维护一套业务接口。真实 GPU 测试由对应设备负责人完成，我则可以通过测试替身验证命令拼装、状态变化、超时、错误和文件校验。这种方式既不会因为没有同样的显卡停工，也不会用模拟结果冒充真实模型成果。

本周的不足是，目前服务层仍处于骨架阶段，尚未建立完整的数据集索引原子写入、任务日志持久化和异常恢复机制，对 GPT-SoVITS 各脚本的具体参数也还不够熟悉。下周我将根据 CXY 提供的真实命令，实现音频处理与训练任务编排；同时补充配置错误、进程超时、输出缺失和 GPU 忙碌等测试，确保后端即使执行失败，也能保持文件和索引一致。后续开发中，我会坚持区分“自动测试通过”和“真实 GPU 通过”，让每个完成结论都有对应证据。
